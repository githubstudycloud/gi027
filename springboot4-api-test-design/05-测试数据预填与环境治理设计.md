# 05 - 测试数据预填与环境治理设计

> 目标：任何用例在任何环境都能"开箱即用"——
> **数据可声明、可复用、可重置、可追溯**。问题复现不再靠"人肉造数据"。

---

## 1. 数据形态分层

| 形态 | 用途 | 生成方式 | 生命周期 |
|------|------|---------|---------|
| **Seed（种子）** | 全环境通用基线（字典、组织、角色） | SQL / Liquibase / Flyway | 随环境创建，长期保留 |
| **Fixture（固定夹具）** | 用例级确定性数据（账号 A / 订单 X） | YAML/JSON + DataFactory | 每用例前重建 |
| **Builder（构造器）** | 编程式构造领域对象 | Java DSL（OrderBuilder.aValid().with...） | 内存级 |
| **Snapshot（快照）** | 复杂场景一键回放 | DB dump + 脱敏 | 按需 |
| **Synthetic（合成）** | 性能/混沌大规模数据 | Faker / 业务生成器 | 临时 |
| **影子（Shadow）** | 生产流量复制 | 流量录制 + 脱敏 | 24h |

## 2. 预填策略（Seeding）

### 2.1 项目内置（推荐）
```
src/test/resources/fixtures/
  ├─ user/
  │   ├─ basic.yaml          # 单个领域基础夹具
  │   └─ locked.yaml
  ├─ order/
  │   ├─ pending.yaml
  │   └─ paid.yaml
  └─ scenarios/
      ├─ login-then-checkout.yaml   # 跨域复合场景
      └─ refund-partial.yaml
```

YAML 示例：
```yaml
fixture: user.basic
description: 一个已注册、未锁定、邮箱已验证的用户
data:
  user:
    id: u_test_basic_001
    phone: "13800000001"
    passwordHash: "$argon2id$..."          # 固定哈希，便于跨环境
    status: ACTIVE
  user_profile:
    userId: u_test_basic_001
    nickname: 张三（测试）
    locale: zh-CN
references: [REQ-2026-001-AC-01]
```

### 2.2 加载机制（不写代码，仅约束）
- 自定义注解 `@Fixture("user.basic")`，在 `BeforeEach` 由 framework 加载到对应数据源。
- 多 Fixture 可叠加，冲突时**后者覆盖**并打 WARN。
- 默认事务回滚；声明 `@Fixture(persist = true)` 可在集成场景保留。
- 加载失败 = 用例失败，且日志带 `fixture:user.basic`。

### 2.3 跨环境 Seed
- `db/seed/<env>/` 下放各环境差异化基线（local / test / beta）。
- 通过 Flyway 版本化迁移，不允许"手 SQL"造数据。
- pro 环境 **禁止 seed**，仅可"导入演练租户"。

## 3. DataFactory（编程式构造）

约束：
- 每个聚合根（Aggregate）有且只有一个 `XxxFactory` 静态入口。
- 默认值必须是"业务可通过验证的最小合法对象"。
- 链式 with：`OrderFactory.aPaid().withItem(...).withAmount(99.9).build()`。
- 涉及外部 ID 用 `Idempotent.next()` 而非 `UUID.randomUUID()`，便于复现。

随机性管控：
- 全局 `TestRandom` 注入固定 seed（CI 中由 commit hash 派生），保证**同一 PR 多次跑结果一致**。
- 失败用例日志必须打印 `seed=...`，便于本地复现。

## 4. 数据预填与契约绑定

OpenAPI 扩展字段（与 02、03 协同）：

```yaml
/v1/users/{id}:
  get:
    x-test-data-ref:
      fixtures: [user.basic]
      examples-from-fixture: true   # 文档 example 自动用 fixture 真实数据
```

收益：
- Swagger / Redoc 的 `example` 自动来自夹具，避免"文档示例与真实不一致"。
- Mock Server 也可读 fixture 作为响应（见 06）。
- 用例骨架生成器读到 `x-test-data-ref` 即自动 `@Fixture(...)`。

## 5. 环境治理（与 [arch-design/07](../springboot4-arch-design/07-环境与部署拓扑设计.md) 衔接）

| 环境 | 数据策略 | 重置频率 | 三方接口 |
|------|---------|---------|---------|
| local | Seed + Fixture，全部容器化（Testcontainers） | 用例级 | WireMock 本地 |
| test | Seed + 每日 Fixture 全量重建 | 每日 02:00 | WireMock 中央实例 + 录制 |
| beta | Seed（脱敏快照）+ 受控写入 | 周级，按需 | 三方"沙箱" + WireMock 兜底 |
| pro | 真实数据，**禁测试写** | 永不 | 真实 |

约束：
- **每个环境独立数据库实例**，禁止共用。
- pro 流量复制到 test / beta 必须经 PII 脱敏 pipeline，明文不得跨环境流动。
- 任何环境的"数据破坏"事故 → 通过 Snapshot 30 分钟内恢复（演练每季 1 次）。

---

## 6. 数据脱敏（强制）

- 字段级标签：`@Pii(level = HIGH)`、`@Sensitive`
- 脱敏规则统一在 `data-masking-rules.yaml`：
  - 手机号 → 中段星号
  - 身份证 → 保前 3 后 4
  - 金额 → 保留量级，扰动 ±5%（性能数据用）
- 任何 fixture / snapshot / 日志（见 07）落地前都过统一 masker，CI 静态扫描敏感词阻断。

---

## 7. 失败可复现性（核心 KPI）

每个失败用例日志必须包含：
- `fixtures=[user.basic, order.pending]`
- `seed=0xC0FFEE`
- `wiremock-recording=20260428-001`（见 06）
- `traceId=...`

凭这 4 个键 + git sha 即可在本地一键复现：
```
./gradlew :user-service:replay --testcase=... --seed=0xC0FFEE --fixtures=user.basic,order.pending
```

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| Fixture 爆炸 / 重复 | 每季清理；Fixture 必须被 ≥ 1 用例引用，否则 CI 警告 |
| 真实数据流入 | 静态扫描 + 入库前 masker 强制 |
| Seed 与业务不同步 | Seed 走 Flyway，与 schema 一起评审 |
| 预填污染共享环境 | 命名空间隔离（test_*）+ TTL 清理 job |
