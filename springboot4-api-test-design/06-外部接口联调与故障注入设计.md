# 06 - 外部接口联调与故障注入设计

> 外部接口是"问题主要来源"。本卷给出**录制即契约 + 分级 Mock + 故障注入**三位一体的方案。

---

## 1. 外部接口的四种形态

| 形态 | 说明 | 处置 |
|------|------|------|
| 有官方 OpenAPI | 大厂主流（阿里云、AWS、Stripe） | 直接落 `contracts/external/`，Prism 起 Mock |
| 仅 PDF / Word 文档 | 老旧 / 国内政企 | 联调阶段抓包 → 转 OpenAPI（手工 + 校验）|
| 仅 SDK 黑盒 | 三方只给 jar | 用 `Adapter` 包裹，Mock 在 Adapter 上方 |
| 异步回调 / WebHook | 需要被三方反向调用 | 自建回调端 + WireMock 充当三方 |

> 核心约束：**所有 C 类调用必须经 `*-integration` Adapter**（见 [arch-design/01](../springboot4-arch-design/01-多模块架构与分层设计.md)），Mock / 录制 / 故障注入只对 Adapter 边界生效。

---

## 2. Mock 分级（金字塔）

| 级别 | 工具 | 适用场景 | 数据源 |
|------|------|---------|--------|
| M1 契约 Mock | **Prism** | 单元/切片/早期联调 | OpenAPI `examples` |
| M2 录制回放 | **WireMock**（recording proxy） | 集成测试，复刻真实三方 | 真实沙箱抓包 |
| M3 行为 Mock | **WireMock** + scenarios / state | 多步交互（OAuth、对账） | 手写 JSON + 状态机 |
| M4 故障 Mock | WireMock + **Toxiproxy** | 故障注入 / 混沌 | 规则注入 |
| M5 真实沙箱 | 三方提供 | 关键链路冒烟 | 真实账号 |

> 组合策略：CI **强用 M1+M2**；预发 **M3+M5**；生产前演练 **M4**。

---

## 3. 录制即契约（关键设计）

流程：
1. 联调期把 WireMock 设为**正向代理**指向真实三方沙箱，自动生成 `mappings/`。
2. 生成的 mapping JSON 经过：
   - **PII masker**（见 05）
   - **Spectral / 自研规则**校验响应符合声明的契约
3. 校验通过 → 落到 `tests/external/<vendor>/<api>/recordings/<日期>-<编号>.json`
4. CI 用回放模式启动 WireMock，加载这些 mapping 作为"事实契约"。
5. 每条录制带元数据：

```json
{
  "id": "20260428-001",
  "vendor": "aliyun-dysms",
  "api": "POST /v2/sms/send",
  "recordedAt": "2026-04-28T10:11:00+08:00",
  "scenario": "登录验证码-成功",
  "linkedRequirements": ["REQ-2026-001-AC-01"],
  "expiresAt": "2026-10-28"
}
```

约束：
- 录制 **过期** 会触发 CI 警告 → 季度联调日重新录制。
- 任意三方 schema 变化（diff）→ 阻塞合并，强制更新契约 + 录制 + 用例。

## 4. 故障注入矩阵（M4）

每个外部接口必须至少配齐以下故障场景（"三必"之二）：

| 场景 | 实现 | 预期行为 |
|------|------|---------|
| 慢响应（> SLA） | WireMock `fixedDelay` | 触发熔断 / 降级 |
| HTTP 5xx | WireMock fault | 进入重试（幂等才行） |
| HTTP 4xx 不合规 | mapping 改字段 | 返回 `IntegrationException` 而非 NPE |
| 限流 429 | WireMock + `state` | 退避重试，最终失败可观测 |
| 网络中断 | Toxiproxy `timeout` | 超时 ≤ 配置值，不卡线程 |
| 慢丢包抖动 | Toxiproxy `latency`+`bandwidth` | P95 不突刺 |
| Schema 漂移 | 改 mapping 多/少字段 | 解析层失败而非业务异常 |
| 证书 / TLS 问题 | WireMock https + 错配证书 | 启动期失败而非运行期 |

落地：故障场景与正常 mapping 平行管理：
```
tests/external/aliyun-dysms/
  ├─ recordings/        # M2
  ├─ scenarios/         # M3
  └─ faults/            # M4
      ├─ slow.json
      ├─ 5xx.json
      └─ schema-drift.json
```

## 5. 联调阶段流程（Inbound 视角）

```
┌────────────┐  代理  ┌──────────┐  真实  ┌────────────┐
│ 本服务用例 │ ─────► │ WireMock │ ─────► │ 三方沙箱   │
└────────────┘        └──────────┘        └────────────┘
                          │
                          ├─ 录制 mapping → masker → 校验 → 入库
                          └─ 同时生成"契约 diff 报告"
```

阶段切换：
- **初始联调**：录制模式（pass-through）
- **稳定联调**：回放模式（仅命中已录制 mapping，未命中报错）
- **故障演练**：注入模式（叠加 faults/）

---

## 6. WebHook / 反向调用

- 自建 `external-callback-controller`，路径 `/callbacks/<vendor>/<event>`，签名校验在 Adapter 中。
- 用 WireMock **充当三方调用方**：在测试中触发 `wiremock.http.post(本服务/callbacks/...)`。
- 必须存在"重复回调幂等"用例与"乱序回调"用例（基于 occurredAt + 业务键）。

---

## 7. 集中化 Mock 服务（中央 Mock）

为降低各团队成本：
- platform-team 提供**中央 WireMock 集群**，按 vendor / env 分实例。
- 业务团队仅维护 mapping 文件 + PR 提交。
- 中央 Mock 暴露：
  - `/__admin` 管理 API（受 IAM）
  - 健康端点 → 接入 02 章连通矩阵

但 **本地开发** 仍跑独立 WireMock 容器，避免相互污染。

---

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| 三方接口"沙箱即真实"，录制污染 | 录制网关强制脱敏 + 不录敏感参数白名单外字段 |
| 录制过期未更新 | CI 计算"录制年龄"，> 6 月警告，> 12 月阻塞 |
| Mock 响应失真（造数据偏移） | 关键链路必须配 M5 真实沙箱冒烟 |
| 三方限流影响联调 | 中央 Mock 兜底，CI 不直连三方 |
