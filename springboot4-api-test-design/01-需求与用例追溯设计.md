# 01 - 需求与用例追溯设计

> 目标：让 **PRD → 验收标准（AC） → 自动化用例 → 缺陷 → 日志关键字** 形成一条可双向追溯的链。
> 不依赖商业 ALM，原生用 Git + Markdown + 注解 + 报告即可闭环。

---

## 1. 需求入仓结构

```
docs/
├── requirements/
│   ├── _template.md                         # 模板
│   ├── REQ-2026-001-用户登录.md
│   ├── REQ-2026-002-订单创建.md
│   └── INDEX.md                             # 自动生成的总目录
└── api/
    └── openapi/
        ├── user-service-v1.yaml
        └── order-service-v1.yaml
```

- 命名规则：`REQ-<年>-<四位序号>-<中文短名>.md`
- AC 编号：`REQ-2026-001-AC-01`，全局唯一，**永不复用**。
- 索引 `INDEX.md` 由脚本扫描生成，禁止手维护。

---

## 2. PRD 模板（核心字段）

```markdown
# REQ-2026-001 用户登录

## 1. 背景与价值
（一句话价值假设 + 量化指标，如：登录成功率从 92% → 99%）

## 2. 用户故事
作为 <角色>，我希望 <能力>，以便 <价值>。

## 3. 范围
- 包含：账号密码、短信验证码
- 不包含：第三方登录（拆 REQ-2026-007）

## 4. 验收标准（AC）
| 编号 | Given | When | Then | 优先级 |
|------|-------|------|------|--------|
| REQ-2026-001-AC-01 | 已注册用户 | 提交正确账号密码 | 返回 200 + JWT，且包含 sub/exp | P0 |
| REQ-2026-001-AC-02 | 任意用户 | 连续 5 次密码错误 | 返回 423，账号锁定 15 分钟 | P0 |
| REQ-2026-001-AC-03 | 锁定中用户 | 提交任何密码 | 返回 423，错误码 USER_LOCKED | P1 |

## 5. 关联接口
- POST /v1/auth/login        （契约：user-service-v1.yaml#/paths/~1v1~1auth~1login）
- POST /v1/auth/refresh

## 6. 关联外部依赖
- 短信网关 SMS-GW（见 02 接口分类）

## 7. 非功能需求
- P95 < 200ms / 单机 500 QPS / 日志含 traceId + userId（脱敏）

## 8. 关联用例
> 由流水线根据 @Tag 自动回填，禁止手写。

## 9. 关联缺陷
> 由流水线根据 commit / issue 自动回填。
```

## 3. 双向追溯实现

### 3.1 代码侧打标
所有自动化用例必须在 JUnit 5 上打 `@Tag`：

```java
@Tag("REQ-2026-001-AC-01")
@Tag("api:POST /v1/auth/login")
@Test
void 登录_正确凭证_返回200和JWT() { ... }
```

### 3.2 契约侧打标
OpenAPI 的 `operation` 节点添加扩展字段：

```yaml
paths:
  /v1/auth/login:
    post:
      x-requirements: [REQ-2026-001-AC-01, REQ-2026-001-AC-02]
      x-owners: [team-iam]
```

### 3.3 日志侧打标
异常 / 关键路径日志中注入需求编号（仅 WARN/ERROR 必带）：

```
WARN  [traceId=ab12 userId=u_***1 req=REQ-2026-001-AC-02] 账号锁定 attempts=5
```

### 3.4 自动回填脚本（设计意图）
CI 流水线中执行：

1. 解析所有 `@Tag("REQ-...")` → 生成 `requirement-coverage.json`
2. 解析所有 OpenAPI `x-requirements` → 生成 `api-coverage.json`
3. 合并写回每个 PRD 的"第 8 节关联用例"，PR diff 形式提交。
4. 任何 PRD 第 8 节为空 = **未覆盖** = 阻塞合并（除非显式标 `@no-test-yet` 并设到期日）。

---

## 4. 覆盖率与门禁

| 指标 | 计算方式 | 门禁 |
|------|---------|------|
| AC 自动化覆盖率 | 已被 ≥1 条 `@Tag` 引用的 AC / 总 AC | ≥ 80% 阻塞 |
| 接口 AC 反向覆盖率 | 已被任意 AC `x-requirements` 引用的 operation / 总 operation | ≥ 90% 阻塞 |
| P0 级 AC 自动化覆盖率 | 同上限 P0 | **= 100% 阻塞** |
| 缺陷复现用例率 | 缺陷修复 PR 中是否包含失败可复现用例 | 100% 阻塞 |

---

## 5. 缺陷反向链接

- 缺陷模板（GitHub Issue / Jira）必须含：
  - 关联 AC 编号（可多个）
  - traceId（来自日志，见 07）
  - 复现 Fixture（见 05）
- 修复 PR 必须：
  - 新增或修改用例并打 `@Tag("BUG-2026-NNN")`
  - 在对应 PRD 第 9 节由脚本自动回填

---

## 6. 风险与边界

- **AC 滥编号**：禁止"AC-99 其他"。AC 必须可机器化判定通过/失败。
- **PRD 漂移**：实现与 PRD 差异 → 必须先改 PRD 再改代码（"文档即代码"）。
- **跨服务需求**：拆为多个服务级 PRD，外加一份 `EPIC-XXXX.md` 做总览，避免一份 PRD 横跨多仓库。
